## 3. 三重交叉验证（这是结论可信的依据）

只报「100% 收敛」是不够的 —— 那可能只是在自己的口径里自洽。做了三层独立核对：

### 3.1 FK 回代：解真的到达目标位姿

| | 位置误差 | 完整姿态误差 |
|---|---|---|
| **探针解（C# DLS）** | 平均 0.089 mm / 最大 0.213 mm | 平均 **0.0066°** / 最大 0.0153° |

解真实命中轨迹目标位姿（0.2mm / 0.015° 级），不是"算出个数就算成功"。

### 3.2 独立限位复核

用纯 Python 从输出明细重算限位/奇异/步长/翻转四项，与探针自报结果**完全一致**（全零违规）。

### 3.3 工具参数反推自校验

用 `_safe.csv` 的已知关节角做 FK，反推 `target − flange` 在法兰系下的位移，对 1467 点取恒定分量：

```
dx: mean=  0.0384  std=0.0737  ✓ 恒定
dy: mean=  2.2143  std=0.0157  ✓ 恒定
dz: mean=450.7565  std=0.0491  ✓ 恒定   ← 这就是 toolLen
```

⇒ 本工序实际工具为 `OffsetX=0.038, OffsetY=2.214, LengthZ=450.756`。

**注意**：这与 `DensoLibrary.Vs087` 的默认工具（`-2.21, 6.77, 453.08`）**不一致**。
后者是主城序按现场标定 T4 记的值，而这条轨迹实际用的是 450 长枪（UI `TxtToolLen` 默认 450）。
工具长度错 400mm 时，逆解会"收敛得很好"却解出完全错误的腕部姿态 —— 残差为零、姿态漂亮、真机撞枪。
探针已把它做成显式参数（`--tool-len` / `--tool-off`），并要求用 `--calib` 自校验。

## 4. 顺带查出的一个重要疑点（未改算法，仅报告）

把探针解与 C++ 安全层写进 `_safe.csv` 的关节角对比：

| | 位置误差 | 枪轴夹角 | 绕枪轴滚转差 | J2/J3 |
|---|---|---|---|---|
| 探针解 | 0.089 mm | — | — | 112° / −83° |
| safe 解 | 0.082 mm | 1.89° | **89.6°** | 27.9° / 88.1° |

两解**腕心只差 18.4 mm**（同一腕位），但**肘部相差数百毫米**（如 `[396,197,228]` vs `[214,105,788]`）
—— 即「肘上 / 肘下」两个不同臂形。两者位置都对得上、枪轴都指向面法向，只是滚转角差 90°。

含义：
- 探针解完整命中目标姿态（0.0066°），是**唯一正确答案**；
- C++ 侧写进 CSV 的关节角**滚转差 90°** ⇒ 若这组数被直接下发，扇形喷幅方向会整体转 90°；
- 两者**不可混用**：J2/J3 差 76°/154°，混用即在切换处大幅摆臂。

这条只作为观察如实记录，**本轮未改任何算法**（用户明确要求「先别改算法」）。
