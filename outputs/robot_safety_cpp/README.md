# 机器人安全层（robot-safety 分支）· C++ 实现 + 上位机集成

> 分支 `robot-safety`。**既有算法源码一行未改**：`spray_traj.cpp` / `spray_traj.h` 完全没动，
> 只在 `CMakeLists.txt` 里把一个新源文件加进同一个 DLL，并在 `Native.cs` 里追加 P/Invoke 声明。
> 结果：10 个回归样本中 **9 个非曲面样本逐字节一致（9/9 IDENTICAL）**，红线守住。
> 上位机（`wpf/SprayTrajViewer`）已经接上：两个页签 + 结论卡 + 风险点标注 + 修正轨迹导出。

---

## 0. 一句话

`spray_traj.cpp` 负责**「喷得对不对」**（面分割、行铺满、姿态连续）；
本层负责**「机器人能不能安全执行」**——可达、关节限位、枪体/连杆撞不撞原始点云、连杆会不会自碰撞、喷角在不在工艺窗口内。
两者编在同一个 `SprayTraj.dll` 里，**互不依赖**：不调用 `robot_safety_check` 时，行为与以前完全一致。

### C ABI

## 2. 三条硬要求怎么落地

### 2.1 内壁法向不朝上 → 加倾斜角（按法向线性给）

倾角不是一个开关，而是**法向偏离朝上程度的线性函数**：

```
α     = 法向与 +Z 的夹角（0° = 正朝上，90° = 竖直侧壁，180° = 完全倒挂）
tilt0 = tiltNonUpDeg × (α / 90°)，封顶 tiltMaxDeg
```

| α | 面的形态 | 基准倾角 |
|---|---|---|
| 0° | 正朝上 | 0°（垂直喷，工艺最优） |
| 30° | 缓坡 | 10° |
| 45° | 斜坡 | 15° |
| 60° | 陡坡 | 20° |
| 90° | 竖直侧壁 | **30°（= `tiltNonUpDeg`，即工艺喷角上限）** |
| 120° | 倒挂内壁 | 40° |
| 150° | 接近倒扣 | 50° |
| `n_z < −0.7` | 朝下悬垂 | 0°（往上扳会顶穿工件，不做线性外推） |

取 90° 作满量程锚点，是因为它物理上就是"面立起来了"的界限：到这里给满工艺允许的倾角，
比侧壁更倒挂的面继续线性增长（必然超工艺，由 `SPRAY_ANGLE` 如实报出来）。

> **为什么 90° 给到最大是 30° 而不是随便一个数**：侧壁是机器人最难应付的形态——末端要
> 绕到面法向附近，腕部只能从侧面斜插进来，翻不过去就撞工件或接近奇异。倾角在这里必须
> 给到工艺允许的上限；再往上（>30°）膜厚就开始明显变薄，那是工艺的账，不是安全的账，
> 所以交给 `SPRAY_ANGLE` 报 P1，而不是偷偷加大。

> 旧实现是阶梯：`n_z < cos45°` 一律给 20°。45° 边界上直接跳 20°，落到轨迹上就是相邻点
> 倾角突跳——这正是实机跟不上的那种"看起来连续、实际一帧一个台阶"。

`tilt0` 只是起点。间隙不够或够不着时按 **固定 5° 网格**往上加到上限 60°；还不行就把
方位左右偏 30°/60° 再试（内壁往上扳常常顶到对面的壁）。

> 网格必须钉在 5° 整数倍上，不能写成 `tilt0 + k·step`。`tilt0` 随法向连续变化，候选相位
> 会跟着漂移：`curved` idx 2990 在网格的 40° 刚好有 +1.18mm 自碰撞间隙，漂移到 36.48°
> 就变成 −1.16mm 的真干涉——同一个物理点，纯数值抖动决定成败。

**倾斜轴默认取"指向上方"**，但整行会被 §2.4 的站位判别改判——见下节。

> 配套修掉一个早停判据的错误：原来"连续 4 档 clearance 变化 < 0.5mm 就停"。可间隙常常早早
> 饱和到 `search` 上限（120mm），饱和区里自碰撞和关节余量仍在随倾角剧烈变化。现在要三个
> 指标都不动才计数，否则会漏掉后面能过关的档位（同样是 2990 那个点）。

### 2.2 倾角改变，距离严格不变（球面旋转）

```cpp
V3 zTool = -unit(d);                     // 工具 +Z = 喷射方向 = −n'
V3 pC    = face + d * standoff;          // d(θ) = Rot(axis,θ)·n
M3 Rc    = frameFromZ(zTool);
```

`|TCP − face| ≡ standoff`，θ 只改喷角。逐点实测 `standoff_err`，**10 个样本全部 0.000000mm**。

> ⚠ 这里最容易搞反的一条：工具 **+Z 是 −d，不是 +d**（`d` 是外法向，`(I,J,K)` 是 −n）。
> 搞反的症状极具欺骗性——位置全对、喷距守恒、数字都"正常"，但 IK 只能选"反腕 + 大臂下探"的解
> （θ2=154°、J2 超限 19°、小臂从工件底下穿过去 24.7mm）。当时差点误判成"工位摆位不合理"去改基座。

### 2.3 碰撞：判的是**整条臂**，不是只判末端

* **工件碰撞**：关节球 + 6 根连杆 + 握把 + 细管 + 喷嘴，共 20 个胶囊（A-B 轴 + 半径），
  每段都对 KD-tree 点云求线段最短距离，`surface = 距离 − 半径`，`<0` 即穿透。
* **按部位分开报**：枪体（握把/细管/喷嘴）与连杆/关节/底座分别给最小距离，并报出**最近的是哪一段**
  （`连杆J3-J4`、`关节J4`…）。
* **自碰撞**：非相邻连杆胶囊两两之间，Ericson 5.1.9 解析解（排除"同一关节球 + 它自己的两根连杆"）。
* **可达/限位/奇异**：阻尼最小二乘 IK，种子顺序 = 上一点解 → 解析种子 → 固定种子表；
  关节软限位余量；归一化雅可比（位置行 ÷ 500mm）条件数。

> **为什么要分开报**：这两类撞车的处置完全不同——枪体撞改喷距/喷角就行，连杆撞必须改站位或
> 整条轨迹的姿态。混成一个"最小距离"，现场拿到 −8.57mm 也不知道该动哪儿。实测 `longstripe`：
> **枪体 20.09mm（安全），连杆 `连杆J3-J4` −7.24mm（穿透）**——只看喷嘴会把它判成通过。
> `big` 同理：枪体 47.14mm 很宽松，连杆 `J3-J4` 29.68mm 才是真正压线的那个。

> **修掉一处真实漏判**：原来为了省时间，`linkStride=3`——每 3 个点才判一次连杆，其余 2/3 的点
> 只判枪体。也就是说"连杆会不会撞"这件事，**有三分之二的点根本没查**。现在逐点全判；
> 性能靠剪枝拿回来：某段连"当前最差表面距离 + 半径"都够不着时直接跳过 KD 查询，
> 全量 10 样本仍只要 22 秒。

半径唯一来源 `ArmSizing.From`（reach 905）：关节 34.39、J1 42.99、连杆 21.32、腕 24.76、
握把 21.32、细管 9.59、喷嘴 6.39。

### 2.4 进刀侧：从"重力朝上"改成"按机器人站位"，但只用来救 P0

倾角是**多大**，方位是**从哪一侧压过来**。两者是独立的自由度，早期版本把方位写死成
"把法向往 +Z 扳"，只有失败时才左右偏 30°/60° 兜底。这个假设的物理依据很弱：
内腔里"上方"经常正对着对面的壁。

现在改成逐行在「向上」与「站位侧」之间择优。站位侧的定义：机器人基座必然立在工件之外，
把 `基座 − 加工点` 投到切平面，枪就往那一侧倾（枪身落在工件与基座之间，腕子不必伸进腔体）。

```
az_stance = atan2( u·(n×uUp), u·uUp )     u = unit((base−face) − n·((base−face)·n))
基座几乎在法向延长线上（切向分量 < sin20°）→ 无倾向，不参与选择
```

**方位是行级常量，不是逐点量**：逐点变等于沿轨迹反复拧腕，实机执行不了；阶段 3 本来
就按行取一个方位。所以决策也在行级，而且必须在**倾角定下来之后**（见下面的翻车记录）。

判据只有一条：**P0 上严格更安全**（穿透 → 不可达 → 自碰撞，字典序）。间隙变大、
关节余量变好、喷角变小这些都**不换方位**——它们是倾角大小的账，不是方位的账。
采样先稀（5 点）后密（≤120 点），稀采样看不出 P0 优势就直接放弃。

| 样本 | P0 点 | 连杆穿透 | 不可达 | 间隙告警 | 枪体最小 | 连杆最小 | 改写行数 |
|---|---|---|---|---|---|---|---|
| 其余 9 个样本 | 不变 | 不变 | 不变 | 不变 | 不变 | 不变 | **0**（逐字节相同） |
| longstripe 关 | 104 | 40 | 64 | 366 | 20.09mm | −8.56mm | — |
| longstripe 开 | **57** | **21** | **36** | **255** | 20.09mm | −7.24mm | 2/45 行 |

> **为什么"其余 9 个样本一个字节都不变"比"longstripe 变好"更重要**：说明这层是
> 安全兜底而不是又一个全局优化器。旧口径本来就安全的件，结论、位姿、CSV 全部照旧，
> 现场存档可以直接对比；只有旧口径真的撞了的行才动手。
>
> longstripe 的代价要如实写出来：关节超限 +7 点、喷角超工艺 +32 点、近奇异 +4 点、
> 倾角均值 +0.1°。换来的是 47 个 P0 点、19 个连杆穿透点、28 个不可达点、111 个间隙告警消失，
> 而枪体最小间隙**没变差**（20.09mm 持平）——**这笔账在本分支的优先级下是划算的**。

**三次翻车，都是同一个病根：判据与被判的对象不一致。**

1. **在 `tilt0` 上判 P0。** 阶段 1 之前就定方位，只能用线性基准倾角打分。`complex` 有一行
   实际执行倾角是 40~55°（倾角搜索为了躲碰撞自己加上去的），而 `tilt0` 只有 20°：
   在 20° 上"向上撞、站位不撞"，到真倾角上完全不成立。结果换完方位冒出 **110 点关节超限**，
   连杆间隙从 77mm 掉到 37mm。→ 把决策挪到倾角定下来之后，按 `finalTilt[i]` 打分。
2. **拿"向上"当基准，见到非零就跳过。** `longstripe` 两行的方位其实已经是 ***30°***（阶段 1
   兜底换的），而守卫条件写的是 `if (azRow != 0) return;` → 最需要救的两行根本没进决策，
   阶段 2.5 只花了 **0.3ms**。→ 候选集必须包含"当前真正执行的方位"，不能假设它是 0。
3. **用抽样做全局优化。** 最初的打分是"违规点数少 + 间隙大"，`complex` 上换掉 4 行后
   `NEAR_SINGULAR` 39→0、`SPRAY_ANGLE` 716→606（都是好消息），但关节超限 0→110、
   连杆间隙 77→37mm。一行 400~5700 点，抽 5~24 个点判断不了一行的瓶颈在哪。
   中途还试过"拿到真实倾角后再复核一遍方位"，复核说更好、阶段 3 的 `poseCmp` 逐点一比
   又把整行退回旧位姿（`complex` 回退 852→1215 点，输出与旧口径逐字节相同），白花 15~20% 时间。
   → 结论：**行级方位只能用来救 P0，不能当姿态优化器**；要真按"最差点"决策，就得整行
   逐点评估两个方位 = 2× 阶段 1 的开销（阶段 1 已占 84%），产线不接受。

`azStanceRows` 报的是**实际生效**的行数（改判了但被逐点回退掉的不算），不是"改判行数"——
`complex` 上就出现过"改判 1 行、实际一点没变"，报改判数会让现场以为这层做了什么。

旧口径方位完整保留：`-azmode 1`（界面"进刀侧方位 → 只用「向上」"）即回到"方位全向上"的结论，
用于和历史存档对拍。

### 2.5 行 = 一笔，不是"一段连续 spray"

做方位时挖出一个更基础的问题：**安全层对"行"的定义是错的。**
原来是「连续 `spray=1` 的一段」当一行；但母版生成器**跨折返不关喷**，于是：

| 样本 | 生成器切出的笔画 | 安全层原来的"行" | 后果 |
|---|---|---|---|
| longstripe | 45 | **2** | 22 笔共用一个进刀侧；倾角"只升不降"跨折返传递 |
| complex | 36 | 12 | 同上，程度轻一些 |
| tray | 19 | 2 | 同上 |

现在按**折返**断行：水平投影方向与"本笔起始方向"夹角 > 120°（`dot < cos120°`）即断。
不用三维方向是因为曲面/法向变化会让三维步长抖动，而折返在水平面上一定掉头；阈值取 120°
而不是 90°，是为了不把曲面上一笔正常的连续转向切成两行。断点落在折返圆弧里（≈120° 处），
正是两笔之间该断开的位置。切出来的行数与生成器自己报的笔画数完全对上（45/36/19）。

**只改这一处（方位仍全向上）的实测效果**：

| 样本 | 指标 | 改前 | 改后 |
|---|---|---|---|
| longstripe | 关节超限 | 885 | **307** |
| | 不可达 | 71 | **64** |
| | P0 | 111 | **104** |
| | 平滑回退 | 6989 | **4017** |
| | 违规条目 | 7400 | **6849** |
| curved | 违规条目 | 360 | **332**（喷角 336→307、关节 1→0） |
| complex | 平滑回退 | 852 | **206**（违规 764→766，持平） |
| 其余 7 个 | — | — | 逐字节不变 |

原因很直白：把 22 笔当成一行时，"只升不降"的倾角平滑会把上一笔的高倾角一路传下去（多余倾角
= 多余的关节超限与喷角超工艺），方位也只能给一个。**行切对了，这两件事才对。**

顺带把并行粒度也修好了：阶段 3 的任务数从"2 行"变成"45 行"，`longstripe` 8 线程
**5572 → 3735 ms**（−33%），单线程也从 16077 → 14836 ms。

## 3. 一个反直觉但必须守住的优先级

**倾角与间隙不是单调的。** `complex` 的 idx 3163 实测：

| 倾角 | 0° | 20° | 45° | 55° |
|---|---|---|---|---|
| 间隙 | 14.2mm | **18.3mm** | 5.6mm | **−2.4mm** |

加大倾角在这里**不是变好，而是变坏**。而"只升不降"的限幅平滑隐含假设了"倾角越大越安全"，
"整行统一倾斜方位"又让个别点被统一方位顶进工件——两处都在**拿 P0 碰撞换 P2 姿态平滑**。

改法：平滑后的位姿只要比本点最优更差（自碰撞通过 / 间隙 / 关节余量逐项比较），就退回本点最优，
记 `reverted`。代价是姿态可能跳一下，由 `TILT_JUMP`（P2）报出来。

效果：`complex` 由穿透 **−5.81mm** → 最小间隙 **+19.87mm**，回退 853 点。

### 4.4 耗时与生产节拍

生产上没人在产线等 16 秒，所以这一节是硬指标。先看时间花在哪（12 核机器，`RS_PROFILE=1`）：

```
longstripe（11558 点 / 22 万点点云）
  [prof] 点云KD构建     182 ms      1%
  [prof] 阶段1 求倾角  13531 ms     84%   ← 6.9 万次 IK + 93 万次点云查询
  [prof] 阶段3 重解     2306 ms     14%
  [prof] 总计          16077 ms
```

**两个加速手段，默认都关着或可调**：

| 手段 | 参数 | 效果 | 代价 |
|---|---|---|---|
| 多线程 | `-threads 8`（界面默认 8） | 阶段 1/3 按点/按行并行，**2.5~3 倍** | 行首点用解析种子自启，个别点可能选到另一条解支（`longstripe` P0 111→110） |
| 点云体素 | `-voxel 3`（界面默认 0） | 大点云 KD 构建快 4~6 倍，**整条流程 3~5 倍** | 薄壁件距离偏乐观（见下） |

实测（同一台机器）：

| 样本 | 点 | 点云 | 单线程 | 8 线程 | 8 线程 + `voxel 3` |
|---|---|---|---|---|---|
| tray | 1323 | 1.4 万 | 187 ms | 166 ms | 186 ms |
| complex | 4989 | 8.4 万 | 984 ms | **488 ms** | 446 ms |
| big | 9761 | 60 万 | 1461 ms | 1205 ms | **735 ms** |
| longstripe | 11558 | 22 万 | 14836 ms | **3735 ms** | 4201 ms |

界面（`--safety 1`，8 线程）实测 `longstripe` 5.4 s，与命令行一致。

> **`voxel` 的精度代价必须说清，不能只看速度。** `longstripe` 用 `voxel 3` 后连杆距离
> 从 **−8.56mm 变成 −1.81mm**，偏乐观 6.75mm——因为它是薄壁长条件，3mm 体素会把薄结构抽稀掉。
> （这一组是改前口径实测；行切分/方位改动不改变体素偏乐观这个结论，量级同源。）
> `big` / `complex` 只差 0.1~1.4mm。所以：
>
> * **出报告、存档、对拍 → `voxel 0`（全量精判）**；
> * 在线预判/拖动参数看趋势 → `voxel 3~5`，但必须以精判为准。
>
> 宁可慢一点，也不要拿"抽稀后没撞"当结论。

**一条没做（也建议先别做）的优化**：给候选倾角复用"上一档的解"当 IK 种子。实测反而慢 7%
（13.1s → 14.2s）——DLS 会顺着那条解支收敛到**更超限**的构型，然后还得回头试其它种子。
这类"看起来聪明"的改动必须实测，不能凭直觉。

## 5. 已知边界

1. **基座位姿是最大不确定项。** 不给 `-base` 时按"工件质心前方 0.50·reach、下沉 0.35·reach"猜一个，
   报告里会显式标注 `baseAuto=1`。可达率低于 90% 基本就是猜错了，必须用真标定值。
   `longstripe` 就是这种情况。
2. **喷角上限 30° 是占位假设。** 交接文档第 184 行把它列为待用户拍板的开放问题。
   它只影响 `SPRAY_ANGLE`（P1，工艺告警），不影响碰撞/可达结论。
3. **点云遮挡**：KD-tree 查的是"点云上的最近点"，看不到被遮挡的背面。这条对**连杆**判定影响很大——
   单视角扫描通常只有正面点，连杆从背面穿过时不会被发现。凹腔深处若背面缺失，结论会偏乐观；
   这一点与 `DensoArmKine` 同源，不额外引入差异。
4. **碰撞是逐点判，不是连续扫掠**：只在每个轨迹点上摆一次臂，不检查两点之间连杆扫过的空间。
   点距 4mm、倾角跳变受 `tiltRateDeg` 限制时足够，但若有人把点距放大到几十毫米，需要另做扫掠检查。
5. **速度/加速度未校验**：本层只判几何与限位，不判关节角速度/加速度是否超限。
6. **`threads>1` 时逐点关节角不可复现**（结论级指标可复现）。并行按块/按行切开，行首点没有
   "上一点解"当种子，改用解析种子自启 → 落到另一条**等价** IK 解支上。§2.5 把行切细之后
   行首变多，这条比以前明显：`longwide` 的 CSV 与单线程逐字节差异上万行。
   实测影响范围（10 个样本，8 线程 vs 单线程）：**结论（PASS/WARNINGS/REJECT）、可达数、
   枪体/连杆最小间隙完全一致**；P1/P2 计数会小幅漂移
   （`longwide` 近奇异 83→117、`longstripe` 喷角 6026→6032、跳变 +3）。
   要存档、要对拍、要申诉逐点姿态 → `threads=1`；只要结论 → 8 线程（快 2.5~4 倍）。
7. **`voxel>0` 会偏乐观**，薄壁件尤其明显（`longstripe` 实测 +6.75mm）。只用于预判。
8. **进刀侧决策靠抽样**（每行稀 5 点 / 密 ≤120 点），不是整行逐点。所以它只敢用来救 P0
   （穿透/不可达/自碰撞的**点数**严格减少才换），不用来比间隙大小——抽样看不到最差点。
   若某行的瓶颈恰恰落在采样点之外，会漏判（表现为"该换没换"，不会"不该换却换了"）。
9. **`azMode=0`（默认，按站位择优）目前只在 `longstripe` 上改判**，其余样本方位仍全部向上。
   收益面还窄；等有更多"连杆撞工件"的真件样本再评估是否扩展到"整行逐点评估两个方位"
   （代价 2× 阶段 1，产线目前不接受）。
10. **入库基线与改前不再逐字节一致**（`complex` / `curved` / `longstripe` 三个样本的
   `trajectory_checked.csv` 已按新口径重生成）。差异全部来自 §2.5 行切分与 §2.4 方位，
   逐项三方差值见那两节；`synth/panel/tray/zhe/cao/longwide/big` 仍逐字节不变。
   **master 分支的 9/9 回归红线不受影响**——这条线约束的是 `spray_traj_generate` 的输出，
   本层是独立入口，一行都没碰。

## 6. 怎么用

```bash
# 编译
cd cpp/SprayTrajCore
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release

# 校验（不给 -base 时用自动假设）
build/bin/Release/spray_safety.exe traj.csv cloud.ply checked.csv

# 给真基座位姿（mm / 度，ZYX 欧拉）
build/bin/Release/spray_safety.exe traj.csv cloud.ply checked.csv \
    -base 1200 0 600 180 0 0 -standoff 100 -safety 20 -tool 150

# 生产提速：8 线程精判（推荐日常用）
build/bin/Release/spray_safety.exe traj.csv cloud.ply checked.csv -threads 8

# 进刀侧：0=按机器人站位逐行择优（默认） / 1=只用「向上」（旧口径，对拍历史存档）
build/bin/Release/spray_safety.exe traj.csv cloud.ply checked.csv -azmode 1

# 在线预判：再叠 3mm 点云体素（快 3~5 倍，但薄壁件偏乐观，别拿它出报告）
build/bin/Release/spray_safety.exe traj.csv cloud.ply checked.csv -threads 8

# 进刀侧：0=按机器人站位逐行择优（默认） / 1=只用「向上」（旧口径，对拍历史存档）
build/bin/Release/spray_safety.exe traj.csv cloud.ply checked.csv -azmode 1 -voxel 3

# 看分段耗时（判断慢在 IK 还是点云）
RS_PROFILE=1 build/bin/Release/spray_safety.exe traj.csv cloud.ply checked.csv -threads 8

# 进刀侧：0=按机器人站位逐行择优（默认） / 1=只用「向上」（旧口径，对拍历史存档）
build/bin/Release/spray_safety.exe traj.csv cloud.ply checked.csv -azmode 1

# 看结构体 ABI 尺寸（与 C# 侧 Marshal.SizeOf 对照）
build/bin/Release/spray_safety.exe --abi
```

输出 CSV：前 8 列按 master 格式原样，中间额外列原样带出，追加
`tilt_deg, clearance_mm, clearance_tool_mm, clearance_link_mm, worst_part, link_part,
self_gap_mm, margin_deg, standoff_err_mm, lifted_mm, cond, reverted, J1_deg..J6_deg, violation`。

* `clearance_tool_mm` 只看枪体（握把/细管/喷嘴），`clearance_link_mm` 只看连杆/关节/底座；
* `worst_part` 是全局最近的那一段，`link_part` 是连杆侧最近的一段（`连杆J3-J4` / `关节J4`…）；
* `violation` 里 `LINK_HIT` 与 `TOOL_HIT` 分开，不再混成 `COLLISION`。

未测到的值写 `nan`（不是 0）：IK 失败的点没有位姿，`0` 会被读成"贴脸 0mm"。
同目录另写 `trajectory_checked.csv.base.json`（`T_base_in_cloud` + 参数），供对拍时复用同一个基座位姿。

退出码：`0` 无 P0（可执行）、`1` 有 P0（撞了/不可达）、`2` 参数或读文件错误。

### 6.1 上位机集成（`wpf/SprayTrajViewer`）

界面上线了，不再只是代码可调用。左侧拆成两个页签，两个主按钮都在首屏：

| 页签 | 内容 |
|---|---|
| **轨迹生成** | 原有点云/工艺参数/生成按钮 + 显示控制（新增「标记风险点」「显示修正后轨迹」） |
| **机器人安全** | 基座位姿（自动假设 / 手填标定值）、工具长、安全间隙、工艺喷角上限、倾角搜索上限、关节余量、**并行线程数**、**点云体素**；「机器人安全评估」与「导出修正后轨迹 (CSV)」两个按钮；本页内嵌一份结论 |

右侧 3D 视图右上角固定一张结论卡：结论（PASS / PASS WITH WARNINGS / REJECT）、耗时、
可达率、最小表面距离、**枪体最小（含部位）/ 连杆最小（含 `连杆J3-J4` 这种段名）**、喷角均值/p95/最大、

**风险点分三层画**，否则几千个喷角超限点会把工件糊成一片、反而看不出真正的坑：

| 颜色 | 含义 | 画法 |
|---|---|---|
| 红（大点） | P0 碰撞 / 不可达 / 自碰撞 | 逐点全画 |
| 橙（中点） | 间隙不足 / 关节余量不足 | 逐点全画 |
| 黄（小点） | 喷角 / 接近奇异 / 倾角跳变 | 抽稀到 ≤400 个，只指示区段 |

青色叠加层是**倾斜修正后**的轨迹，默认关闭（多数样本与红色原轨迹重合，开着只会遮挡）。
连线判据用**原轨迹**相邻点距，不用修正后距离——倾斜会让点整体挪开 2·standoff·sin(θ/2)，
按修正后距离判会把每一行都判成断开。

## 7. 附：Python 原型

`robot_safety/`（2526 行）是最初的原型实现，用来快速试算法与做交叉验证，
**不是产品路径**。倾角策略改成线性后两边同源（`_need_tilt` 与 `needTilt` 用同一套候选：
线性基准 + 固定 5° 网格 + 三项早停），逐点对数的差异只来自点云抽稀（C++ 全量、Python 抽稀到
25000 点）与 IK 收敛路径，量级都在千分位。
两者都保留，改算法时可以先在 Python 里试，再落到 C++。
